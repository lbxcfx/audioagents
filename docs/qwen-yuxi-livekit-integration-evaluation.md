# Qwen Audio Agent、Yuxi 与 LiveKit 企业多模态客服集成评估

更新时间：2026-07-30

## 1. 评估对象与结论

本次已在本地检出并阅读以下上游仓库：

| 项目 | 本地位置 | 评估提交 | 许可证 | 结论 |
| --- | --- | --- | --- | --- |
| Qwen Audio Agent | `/root/workspace/reference-repos/qwen-audio-agent` | `c41b142b81d96123f3b6895fcc9c693c8a3d3607` | Apache-2.0 | 参考实时语音前台与后台 Agent 解耦，不直接整体嵌入 |
| Yuxi | `/root/workspace/reference-repos/Yuxi` | `1bfe887956d405ee81d02c53820a1190d95ee183` | MIT | 参考知识库、文档任务、MCP注册和前端交互，不直接合并整套平台 |

总体结论：方案可行。当前系统适合继续以 LiveKit 作为实时会话与媒体平面，以 Qwen Audio Realtime 作为低延迟语音大脑，新增独立的企业知识服务和受控 MCP 工具网关。视频需要拆成三个不同能力判断：

1. **人与人工客服视频通话：可直接支持。** LiveKit 原生传输摄像头、屏幕共享、音频和数据。
2. **AI数字人视频输出：可支持。** Qwen生成语音，数字人服务根据语音合成口型和视频，再作为LiveKit参与者发布视频轨道。
3. **AI看懂客户摄像头或屏幕：LiveKit能传，但当前Qwen Audio模型不能看。** 必须增加视觉模型或切换到支持图像/视频的Qwen Omni Realtime。

因此不应把“LiveKit支持视频”误写为“当前语音模型已经支持视频理解”。

## 2. Qwen Audio Agent仓库分析

### 2.1 实际技术边界

该仓库是Node.js实现的个人实时语音Agent运行时，前端包括Web、TUI和macOS桌面端。其Gateway直接连接DashScope Realtime WebSocket，并不使用LiveKit。默认模型为 `qwen-audio-3.0-realtime-plus`。

其核心不是普通的“语音问答”，而是两层结构：

- Realtime frontend：负责全双工语音、打断、短问题和即时反馈。
- Backend Agent：通过ACP连接OpenCode、OpenClaw、Qoder等后台Agent，处理需要工具、文件或较长执行时间的任务。

实时层只暴露少量受控工具；长任务进入队列后，实时对话仍可继续，完成结果再安全地插回当前对话。这个思路非常适合客服：客户不应因为CRM查询、工单创建或知识检索而面对长时间静默。

### 2.2 可复用设计

- **非阻塞任务编排**：工具执行不阻塞实时语音主循环。
- **一个客户只感知一个助手**：内部检索、MCP和后台任务不暴露成多个Agent。
- **任务状态标准化**：queued、running、completed、failed、cancelled。
- **结果安全回注**：客户说话或发生打断时，延迟播报后台结果，避免重叠。
- **前后台职责隔离**：实时模型不直接获得任意系统权限，只调用经过治理的工具。

### 2.3 不建议直接复制的部分

- ACP和编码Agent适配面向个人桌面助理，不是企业客服的核心依赖。
- 本地用户记忆、桌面悬浮球和用户级进程管理不适合多租户SaaS。
- 自建Realtime Gateway与现有LiveKit会话层重叠，整体引入会形成两套房间、身份、并发和断线恢复机制。

正确做法是把其“实时前台 + 后台工作队列 + 结果回注”思想实现到现有LiveKit Worker中，而不是再部署一套Qwen Audio Agent Gateway。

## 3. Yuxi仓库分析

### 3.1 可参考的知识库链路

Yuxi当前主线采用Vue 3、FastAPI、PostgreSQL、Redis、MinIO、Milvus、Neo4j、ARQ Worker，文档解析支持MinerU、PaddleX和RapidOCR。完整链路是：

```text
创建知识库
  → 上传原始文件到MinIO
  → 建立文件与内容哈希记录
  → 异步解析为Markdown/结构化内容
  → 文本分块
  → Embedding
  → 写入Milvus
  → 检索测试/重排
  → Agent回答时返回引用来源
```

值得采用的实现细节：

- 原始文件与解析结果分开保存。
- 用内容哈希避免同一知识库重复上传。
- 上传、解析、索引为不同状态，失败可重试。
- 解析与索引进入后台任务，并向前端持续报告进度。
- 知识库具有访问权限，不是全平台共享。
- 提供独立的检索测试页，显示相似度、重排分数、来源文件和分块。
- Agent只绑定知识库ID，不把整份文档塞进Agent配置。

### 3.2 MCP设计

Yuxi维护服务端MCP注册表，支持 `streamable_http`、SSE和stdio，保存服务器配置、环境变量、请求头和禁用工具，并在Agent运行时按配置加载工具。

该设计可作为交互参考，但客服生产环境需要更严格：

- 浏览器永远不能拿到MCP密钥、Header或环境变量。
- 远程MCP优先使用Streamable HTTP；stdio仅允许管理员安装的受信服务，运行在隔离Worker中。
- 每个企业、项目和Agent分别绑定允许的MCP服务器及工具白名单。
- 写操作必须区分“自动允许、二次确认、禁止”三种策略。
- 每次调用记录Agent版本、会话、工具、参数摘要、结果摘要、耗时和操作者。
- 设置连接、执行和总会话超时；限制返回体大小；敏感字段脱敏。
- 防止知识库文本或客户话术通过提示注入扩大工具权限。

### 3.3 不建议整套搬入的原因

Yuxi是一套完整平台，包含自己的用户、权限、模型、Agent、会话和前端。直接与当前系统合并会产生双重账户、权限和Agent生命周期。Milvus、Neo4j、MinerU、PaddleX全部同时部署也会显著增加首期运维成本。

建议抽取其领域模型和处理流程，在当前FastAPI/PostgreSQL/React体系中重新实现边界清晰的 `knowledge-service`。初期以文档RAG为主，知识图谱不是客服上线的前置条件。

## 4. 视频客服能力评估

### 4.1 LiveKit可以做什么

LiveKit是WebRTC SFU，可在同一Room传输：

- 客户麦克风和摄像头；
- 屏幕共享；
- AI或人工客服音视频；
- 文本、转写、状态和业务卡片等数据消息；
- AI、客户、人工坐席、数字人等多个参与者。

这足以构建视频客服的媒体基础设施，支持客户从AI转人工时保留原房间、对话上下文和画面。

### 4.2 当前Qwen Audio模型的限制

`qwen-audio-3.0-realtime-plus/flash`的输入是音频和文本，不包含图像或视频。即使前端向LiveKit发布摄像头轨道，当前模型也不能判断安装步骤是否正确、识别票据或看懂客户屏幕。

可选路径：

| 路径 | 做法 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- | --- |
| A. 音频模型 + 抽帧视觉工具 | LiveKit采样关键帧，调用Qwen-VL/Omni HTTP，再把文字观察注入Qwen Audio | 保留现有语音体验；可按需看图 | 视觉不是原生连续上下文；需控制抽帧和延迟 | 首期推荐 |
| B. Qwen Omni Realtime | 视频场景切换为支持音频、图像/视频的Omni实时模型 | 原生理解连续画面 | 需新增LiveKit模型适配、成本和压测 | 第二阶段 |
| C. 只传视频给人工 | AI先语音接待，需要看画面时转人工坐席 | 风险最低、最快上线 | AI不能独立完成视觉判断 | 可作为首期兜底 |

### 4.3 数字人与内容展示

数字人是**输出视频**，不等于视觉理解。推荐链路：

```text
Qwen Audio语音输出
  → 数字人Avatar Worker生成口型/动作视频
  → 作为LiveKit远端参与者发布音视频
  → 客户前端渲染标准LiveKit视频轨道
```

对于产品安装、报销材料、招聘介绍，单纯让数字人口述并不够。应新增一个受控的 `show_content` 工具：

- 从企业已审核的素材库选择视频、图片、PDF页或步骤卡片；
- 通过LiveKit数据通道通知前端展示对应素材；
- 客户可以暂停、翻页或指出当前步骤；
- Agent根据素材ID和客户反馈继续讲解；
- 素材必须是企业已发布版本，模型不得任意生成业务操作视频。

首期最有价值的场景是“数字人讲解 + 审核过的产品视频/步骤卡片”，而不是实时生成视频。实时生成成本高、等待时间长，也更容易出现错误操作示范。

## 5. 推荐目标架构

```text
Web / App 客户端
  ├─ 文本、麦克风、摄像头、屏幕共享
  └─ 数字人、产品素材、引用卡片
                 │
                 ▼
        LiveKit Room / SFU
          │              │
          │              └── 人工坐席 / Avatar Worker
          ▼
   Customer Service Worker
   ├─ Qwen Audio Realtime：语音、打断、即时回答
   ├─ Conversation Orchestrator：状态与后台任务
   ├─ Knowledge Tool：企业RAG检索及引用
   ├─ Vision Tool：按需抽帧识别
   ├─ MCP Gateway：CRM、订单、工单、预约等
   └─ Content Tool：展示审核过的图片/视频/步骤
          │
          ├── Knowledge Service
          │   ├─ PostgreSQL：租户、知识库、文件、版本、权限
          │   ├─ MinIO：原文件、解析结果、展示素材
          │   ├─ Parser Worker：PDF/Office/OCR
          │   └─ Vector Store：Embedding、检索、重排
          │
          ├── MCP Tool Workers / 企业API
          └── Audit & Evaluation
```

关键原则：LiveKit只负责实时媒体和会话传输；模型负责理解与生成；知识服务负责可追溯事实；MCP负责受控业务动作；数字人负责视觉呈现。不要把这些职责混入一个进程。

## 6. 前端产品设计

企业控制台应采用以下主导航，不能继续把“项目与成员”链接到外呼页面：

1. **客服Agent**：角色、服务目标、欢迎语、回答边界、绑定知识库和工具。
2. **知识库**：知识库列表、上传、解析进度、文档预览、分块、检索测试、版本。
3. **业务系统**：MCP/API连接、工具列表、授权范围、连通性测试和审批策略。
4. **体验与评测**：文本、语音、视频三种预览；展示知识引用和工具调用过程。
5. **会话记录**：文本、转写、引用、工具调用、转人工、客户反馈。
6. **展示素材**：产品视频、安装步骤、图片、PDF页面及适用业务场景。
7. **成员与权限**：统一工作空间设置，不属于智能外呼。

Agent编辑页面采用“左侧配置、右侧实时测试”：

- 文本模式默认可用；
- 语音模式显示麦克风和中断状态；
- 视频模式显示摄像头/屏幕共享，并明确提示当前Agent是否具备视觉理解；
- 每条知识回答展示文件名、页码/章节和引用片段；
- 每个MCP动作展示即将执行的业务操作，需确认的动作必须先确认；
- 未命中知识库时明确显示“未找到企业资料”，可一键加入待补知识。

## 7. 分阶段实施

### 阶段一：企业知识语音客服

- 修复智能客服信息架构和成员路由。
- 建立知识库、文件、Agent绑定和权限模型。
- 支持TXT、Markdown、PDF、DOCX上传；异步解析、分块、Embedding和检索。
- Qwen Audio Worker增加 `search_knowledge` Function Calling。
- 文本与语音测试返回引用来源。
- 未命中转人工或创建待处理问题。

验收：同一问题在文本和语音中命中相同知识；引用可追溯；跨企业数据不可见；知识更新后可灰度发布和回滚。

### 阶段二：MCP业务闭环

- 建立企业级MCP注册、密钥托管、连通性测试和工具发现。
- Agent按白名单绑定工具。
- 先上线只读查询，再上线需要确认的写操作。
- 增加幂等键、超时、重试、熔断、审计和权限测试。

验收：能够查询订单/政策、创建工单或预约；重复语音不会重复提交；越权和提示注入不能调用未授权工具。

### 阶段三：视频与数字人

- 前端发布摄像头和屏幕共享轨道。
- 首期采用按需截图 + 视觉工具，并配置人工兜底。
- 接入数字人Avatar Worker。
- 建立企业展示素材库与 `show_content` 工具。
- 对高价值场景评估Qwen Omni Realtime原生视频理解。

验收：客户可展示设备或票据；Agent引用当前帧给出指导；低置信度转人工；数字人音画同步；弱网自动退化到纯语音。

## 8. 风险与上线门槛

- **知识幻觉**：回答必须携带引用和最低检索阈值；低置信度不得编造。
- **工具误操作**：写操作默认确认、幂等、可审计，严禁把MCP密钥暴露给模型或浏览器。
- **文档安全**：文件类型、大小、压缩炸弹、宏和恶意PDF检测；解析Worker隔离运行。
- **视频隐私**：摄像头默认关闭，明确告知用途和保存策略；默认不录制视频。
- **数字人披露**：明确标识AI客服，不冒充真人；使用真人形象或声音需取得授权。
- **性能成本**：视觉抽帧按需触发；Embedding异步批处理；语音路径不能等待长任务。
- **多租户隔离**：所有知识、向量、对象存储和MCP调用都必须带不可绕过的project_id约束。

## 9. 最终建议

建议立即实施阶段一，但不要把Yuxi整体作为子系统运行，也不要用Qwen Audio Agent替换现有LiveKit Worker。最佳集成方式是：

- 保留当前LiveKit和Qwen Audio Realtime语音主链路；
- 将Qwen Audio Agent的非阻塞任务思想移植到Worker；
- 按Yuxi的成熟流程新建轻量、可扩展的知识服务；
- 通过Function Calling把知识检索和MCP工具接入实时模型；
- 视频首期采用LiveKit视频房间、数字人、审核素材和按需视觉工具；
- 对需要连续画面理解的场景，再独立验证Qwen Omni Realtime。

这条路线能先把“基于客户知识和业务系统的语音客服”做扎实，同时保留升级到视频客服的清晰通道。
